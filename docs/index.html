Warp Drive · Layer 3 verifier

Load model adapters only after they pass checks you can replay.

Warp Drive is an open-source verifier for people who run open-weight models on their own machines. It checks an adapter before load, tests it in shadow, records what happened, and can roll it back. The operating system layer around it adds sandboxed tools and recoverable Linux images.

02 // The problemDocumented: README

An adapter you did not verify can change behaviour silently.

A small adapter file can shift what a model says and does. If you load it first and check later, the change is already live.

Warp checks before load and keeps a record after load. If a check fails, the adapter stays off. If behaviour goes wrong later, warp scales the adapter to zero, clears model state, and writes a signed receipt. You can replay every step offline.

03 // How verification worksDocumented: README, ARCHITECTURE.md

Four checks. Each one can stop the load.

1. Check the fingerprints

Warp hashes the checkpoint, its layout and its settings, and compares them with pinned values. A mismatch stops the load before any model code runs.

fingerprint.py

2. Check the numbers

Warp checks adapter size bounds with exact integer arithmetic. No floating point. No rounding gap to hide in.

certificate.py

3. Test in shadow

Warp loads the adapter at scale zero and runs 9 verifier-owned canary prompts. The adapter must not change the answers it should leave alone.

canary.py · 9 canaries, exact count

4. Record and roll back

Warp writes a signed, hash-chained receipt for every mount, reject and rollback. The kill switch scales the adapter to zero and clears state.

ledger.py · verifier.py

04 // The operating system layerPlanned: PLAN.md milestones 3 and 4

Layer 3: the gatekeeper between agents and models.

The README places warp at Layer 3 of a five-layer stack. Above it sits the agent loop. Below it sits the model server. Warp trusts neither side without checks.

The daemon is called warp-modeld. Around it, the repo carries blueprints for sandboxed tools and for Linux images that recover in one reboot. The image build, the boot test and the three-machine rollout are planned work. They have not run yet. See the architecture and the blueprint list.

06 // Try itExact: pyproject.toml

Run the checks offline.

Warp needs Python 3.11 or newer. Runtime dependencies: none. Building the package needs setuptools 68 or newer.

PYTHONPATH=src python3 -m pytest tests/ -q
PYTHONPATH=src python3 -m unittest discover -s tests -v

The second command alone misses two pytest-only test files. Run both, or run pytest for the full count.

07 // LimitsStated plainly

Limits, in full sentences.

Cerebras support is mocked and live use is unverified. The client targets a Kimi model id. Only mocked contract tests pass. A dedicated endpoint may be required.

The lattice backend is simulated. No real lattice model file has run through warp.

The live demo has not run. Its thresholds are preregistered and unverified live. Its tokenizer digest is unverified.

Live timings in the README have no artifact in the repo, so this site does not repeat them as facts.
